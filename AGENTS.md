## Заставка при запуске (cli/splash.py)
* `show_splash(show_traceback, verbose, console=None)` печатает титул «СОБИРАТЕЛЬ РАСШИФРОВОК» блочными глифами `█` (таблица `_GLYPHS` — только 14 букв названия, 5×5; pyfiglet не годится — кириллицы в FIGlet-шрифтах нет) + описание/версию/дату. Вызов — в `cli/main.py` `main()`, после предупреждений о неизвестных аргументов и до loguru-шапки; вывод в stdout (как блоки пауз в `pipeline/executors.py`), шапка loguru не тронута.
* Рендер по приоритету: rich-панель `box.DOUBLE` (`rich==15.0.0` в `requirements.txt`) → голый `print()` при `ImportError` → ASCII-фолбэк (`█`→`#`, рамка `+-|`), если кодировка stdout не тянет блоки/рамку. **Строки центрируются только в `build_splash_lines`** — `Text` в `_render_rich` создаётся **без** `justify`: rich при `justify='center'` отбрасывает хвостовые пробелы строк и центрирует заново, из-за чего верхняя часть слов сдвигалась вправо (у глифов разное число хвостовых пробелов). Между словами титула — пустая строка-разделитель (`TITLE_ROWS` = 11). **`show_splash()` никогда не бросает исключений** (пишет в DEBUG-лог) — декоративный блок не должен останавливать конвейер; не добавляйте в него новых жёстких проверок.
* Управление: `SHOW_SPLASH` (`config/settings.py`) и CLI-флаг `--no-splash` (`cli/arguments.py`, `no_splash` в `main()`). При смене `APP_NAME` дорисуйте глифы новых букв — иначе `_render_word` бросит `ValueError` (глотается, заставка исчезнет). Смоук — `_smoke_splash.py`.

## Автосортировка выгрузок (00_inbox)
* Пользователь выгружает файлы из 1С одним движением в `_INPUT_DATA/00_inbox`; раскладку выполняет `io_module/auto_sort.py` из пауз (`pipeline/executors.py`), под флагом `AUTO_SORT_ENABLED` (`config/settings.py`).

* **Волна 1** (`pause_for_osv_general_export`, до Фазы 0): `prepare_general_osv_from_inbox()` —
  1. Собирает список файлов Общей ОСВ в `inbox` (признак `_общаяосв_` в имени).
  2. **Если в inbox ЕСТЬ Общая ОСВ** — архивирует **ВСЁ** содержимое `general_osv`
     (старую ОСВ + левые файлы), затем переносит свежую ОСВ из inbox с разрешением конфликтов.
  3. **Если в inbox НЕТ Общей ОСВ** — архивирует только левые файлы (без признака `_общаяосв_`),
     существующая ОСВ остаётся на месте (совместимость с чистым стартом).
  4. Очистка остальных целевых папок (`accounts_osv`, `special_reports`, `accounts_osv_lease`,
     `transaction_report`) от чужой Общей ОСВ — файлы с признаком `_общаяосв_` архивируются,
     так как не принадлежат этим папкам.
  Не-ОСВ файлы `general_osv` — в архив (существует параллельно с новой логикой).

  Это устраняет ошибку «TooManyFilesError: в папке найдено 2 файла по паттерну '*_общаяосв_*.xlsx'»,
  которая возникала, когда в `general_osv` из прошлого прогона лежала чья-то Общая ОСВ.

* **Волна 2** (`pause_for_1c_export`, после шага 1a): `sort_inbox_by_expected_list(context)` — источник истины список выгрузок `Выгрузить_<компания>_<период>.xlsx` (листы «Обязательные выгрузки» + «Спецотчеты», колонки «Имя файла для сохранения» → «Куда класть»). `build_expected_map()` возвращает `{норм.имя: (целевая_папка, эталонное_имя)}`; `sort_all()` выполняет ревизию целевых папок (левое — в архив, misplaced — по назначению, кривое имя — `_rename_to_canonical`) и раскладку inbox (`_move_to_dir`).

* **Чтение списка устойчиво к формату шага 1a:** колонки ищутся без учёта регистра (`Куда класть` vs `куда класть` из справочника «Выгрузки»), строка заголовка — в первых 10 строках листа (лист «Спецотчеты» отформатирован с двумя служебными строками сверху).

* **Правила:** классификация только по имени файла (`normalize_name`: нижний регистр, пробелы → `_`, хвостовое `_` опционально; расширение значимо); при совпадении со списком кривое имя **переименовывается к эталону** — иначе `find_register_file` (`utils/file_utils.py`) не распарсит период/счет; содержимое файлов не читается (кроме сравнения хешей при конфликте имён).

* **Конфликты/архив:** ничего не удаляется безвозвратно — `_INPUT_DATA/_archive/<run_id>/<имя_папки>/` (левые файлы, старые версии при перезаписи), нераспознанное — `_archive/<run_id>/unsorted/` с WARNING; конвейер не останавливается (нехватку обязательных файлов штатно сообщит шаг 1b). Идентичный по содержимому дубликат — копия удаляется. Сам файл списка `Выгрузить_*.xlsx` из inbox и `~$`-файлы Excel не трогаются. При наличии Общей ОСВ в inbox старая Общая ОСВ в `general_osv` будет заменена с разрешением конфликтов (в архив уйдёт старая версия). Копия общей ОСВ, оставшаяся в inbox (её нет в списке выгрузок), обрабатывается как в волне 1 — в `general_osv` с разрешением конфликтов.
* **Отчёт:** каждая волна пишет свой лист `sort_report.xlsx` (файл/действие/откуда/куда; листы «Волна 1»/«Волна 2») в папку запуска + INFO-сводка `[SORT]` в лог. Служебные `~$`-файлы Excel не трогаются. Смоук — `_smoke_auto_sort.py` (временные папки, реальные `_INPUT_DATA` не затрагиваются).
* **Очистка архива:** `_INPUT_DATA/_archive` растёт на каждом прогоне, поэтому его старые папки удаляются при старте — `cleanup_old_archive()` (`io_module/auto_sort.py`), вызов в `cli/main.py` сразу после `cleanup_old_runs()` (до пауз и автосортировки, поэтому архив текущего запуска ещё пуст и не может пострадать). Та же ручка `KEEP_LAST_RUNS` (=5) и тот же верхний предел `MAX_KEEP_LAST_RUNS`. Особенности: удаляются **только подпапки** (файл `sort_report.xlsx` в корне архива, который пишет запуск без `configure_run`, не трогается); порядок — **по mtime папки**, а не по имени, потому что в архиве есть папка `manual` (запуск без `run_id`) и при сортировке по имени она считалась бы самой новой и вытесняла бы настоящие прогоны; папка текущего запуска (`get_run_id()`) исключена из удаления; занятый файл (Excel) → WARNING, папка уйдёт при следующем запуске; нет корня — тихий выход. Смоук — `_smoke_archive_cleanup.py` (7 сценариев, временный каталог через параметр `archive_root`).

## Титульный лист отчёта («О отчёте»)
* Первым листом итогового Excel-файла идёт лист `О отчёте` — его собирает `io_module/report_cover.py` (`build_cover_rows(context, warnings=None)`), записывает `write_cover_sheet(writer, rows)` внутри `DataSaver.save_combined_report` (`data_io.py:620`); вызов — `safe_build_cover_rows(context)` в `save_results` (`pipeline/executors.py`). Модуль **не импортирует** `pipeline.base`/`pipeline.steps`: читает только атрибуты `context` и `context.data`, поэтому `io_module` не зависит от шагов.
* Содержимое: заказ (компания, период + тип периода, сегмент, валюта и дата перевода остатков, файл общей ОСВ, `run_id`, время формирования); статусы (увязка ЧП = НРП из `OpuReportConstants.MISMATCH_DIAGNOSTICS_KEY`, сверка ОСВ с выгрузками из `ReconciliationConstants.SUMMARY_KEY` (заполняет шаг 1c), счётчики строк); **ключевые цифры** (актив, пассив, расхождение, выручка — раздел `КЛЮЧЕВЫЕ ЦИФРЫ ОТЧЁТА`); режимы сборки из флагов `config/settings.py`; применённые допуски; легенда листов; список диагностических файлов прогона (`mismatches/`, `warnings/`, `sort_report.xlsx`).
* **Подпись файла диагностики — по его природе, а не по папке.** Папка `mismatches/` неоднородна: туда пишутся и настоящие проблемные данные (`mismatch_*`, `missing_files_*`), и файлы, создаваемые при **штатной** работе шагов (аудит индивидуального меппинга `reference_scope_*`, отчёты свёртки `step20_collapse_opu_*` / `step21_collapse_balance_*` — последние пишутся при каждом прогоне). Одна подпись на всю папку («требуют правки справочников») заставляла получателя искать ошибки там, где их нет. Теперь `_diagnostic_hint()` выбирает подпись по имени: префикс из `DIAGNOSTIC_INFORMATIONAL_PREFIXES` → `INFORMATIONAL_HINT` («сводная информация о работе программы, правок не требует»), иначе дефолт папки (`mismatches/` — «проблемные данные — требуют разбора»). Порядок в `_files_in_folder()` — сначала требующие разбора, потом информационные (`_is_informational` как ключ устойчивой сортировки): на титуле порядок читается как приоритет. Новый диагностический файл по умолчанию попадёт в «проблемные» — при штатной работе добавляйте его префикс в константу, иначе получатель увидит ложную тревогу.
* **Имена листов объявлены в `report_cover.py`** (`COVER_SHEET`, `SHEET_BALANCE`, `SHEET_BALANCE_SOURCE`, `SHEET_PNL`, `SHEET_PNL_SOURCE`) и импортируются в `data_io.py` — не дублируйте строковые имена листов в коде. Цвета ярлычков — `TAB_COLOR_COVER` (синий), `TAB_COLOR_REPORT` (зелёный), `TAB_COLOR_SOURCE` (серый); автофильтр и закрепление шапки ставит `_apply_excel_formatting(data_io.py:530)` (принимает `tab_color`).
* **Единый формат чисел:** `config/defaults.py` — `format_amount()` (разряды пробелом: «4 321») и `format_tolerance_value(key, value)` («3 000 тыс.ед.» либо «22%» для долей из `FRACTION_PARAMS`). Используются и в консоли (`cli/main.py`), и на титульном листе — не форматируйте допуски вручную: раньше доли печатались как «0».
* Титульный лист — справочная информация, а не результат расчёта: обёртка `safe_build_cover_rows()` при любой ошибке логирует WARNING и отдаёт пустой список (отчёт сохраняется без листа).
* **Сводка предупреждений (блок 3):** `logging_handling/logger_config.py` собирает все `logger.warning(...)` за прогон в счётчик (`_collect_warning_sink`, sink уровня WARNING, фильтр отбрасывает `file_only`-записи библиотек). `format_warnings_summary()` даёт готовые строки («текст (×N)», обрезка до 200 симв.) — их печатает `_log_warnings_summary()` (`cli/main.py`) в конце прогона и передаёт `save_results` в `report_cover`; на листе показываются первые `COVER_WARNINGS_LIMIT = 12` строк, остаток — одной строкой со ссылкой на лог. Тот же текст в консоли и в файле — не форматируйте предупреждения на каждом новом месте.
* Смоук — `_smoke_report_cover.py` (54/54, `SMOKE_OK`) и `_smoke_warnings_summary.py` (18/18, коллектор loguru, `SMOKE_OK`).

## Ключевые цифры отчёта (консоль и титульный лист)
* Блок `ИТОГ ПРОГОНА` печатается в конце прогона **до** сводки предупреждений: `log_run_summary(context)` (`io_module/run_summary.py`) вызывается из `cli/main.py` сразу после `save_results()`. Показывает актив, пассив, расхождение `актив - пассив` с вердиктом по `tolerance_balance`, выручку из ОПУ, счётчики строк и статус увязки ЧП = НРП. Те же цифры получатель находит на титульном листе, не открывая табличные листы.
* **Единый источник цифр:** актив, пассив, их расхождение и выручку считает **один** источник — `report_cover.collect_figures(context)` (`io_module/report_cover.py`). Его читают оба представления: титульный лист (раздел `КЛЮЧЕВЫЕ ЦИФРЫ ОТЧЁТА`, между `СОСТОЯНИЕ ОТЧЁТА` и `ПРЕДУПРЕЖДЕНИЯ ЗА ПРОГОН`) и блок в консоли (`io_module/run_summary.py`, который добавляет только счётчики строк и статус увязки — на листе они есть в других разделах). Файл и консоль разойтись в числах не могут: если добавляете новую цифру, добавляйте её в `collect_figures`, а не в оба модуля сразу. Приоритет имён колонок — `ReportLayoutConstants` в `pipeline/step_config.py`.
* Модуль **не проверяет данные повторно**: все числа берутся из уже собранных `context.balance_df` / `context.pnl_df` — ровно тех строк, что попали в книгу. Итоговый баланс = сумма строк по значению колонки `Актив/Пассив` (`ReportLayoutConstants.ASSET_SIDE`/`PASSIVE_SIDE`); выручка — модуль суммы строк с `1 уровень` = `Выручка` (в ОПУ доходы со знаком «-»).
* **Итог листа ОПУ нельзя выдавать за прибыль**: он не равен прибыли периода (НРП накопительный). Прибыль не показывается ни в консоли, ни на листе — её роль играет статус увязки, который берётся из того же источника, что и раньше: `pnl_balance_status_text(context)` (`report_cover.py`, переименована из приватной `_pnl_status_text` — переиспользуется двумя потребителями).
* Числа печатаются в знаках отчёта (пассив с минусом) и тем же `format_amount`, что и файл. Копеечное расхождение не даёт «-0» (`_amount_text` в `report_cover.py`).
* `format_run_summary()` возвращает **список строк**, а не одну строку: консольный формат логгера печатает `short_message` с обрезкой до 500 символов (`logger_config._patch_record`), и блок целиком в одну запись обрезался бы.
* Отсутствующие таблицы/колонки дают «—» или «расшифровка не собрана», а не исключение; `log_run_summary` ловит всё и логирует WARNING — файл отчёта уже сохранён, код выхода не меняется.
* Имена колонок отчётных листов объявлены в `pipeline/step_config.py` (`ReportLayoutConstants`) — им пользуются шаги 20/21 (`collapse_base.py`) и `io_module`. Не дублируйте эти строки в новом коде. Смоуки — `_smoke_run_summary.py` (цифры реального прогона + сверка консоли с листом) и `_smoke_report_cover.py` (раздел `КЛЮЧЕВЫЕ ЦИФРЫ ОТЧЁТА`).

## Автоматическая постобработка и валидация
При вызове `Step.execute()` (`base.py:136`) автоматически (не пишите ручной код):
1. `_validate_input(context)` — валидация входа
2. `_process(context)` — бизнес-логика (единственное место для кода шага)
3. `_clean_whitespace(context)` (`base.py:491`) — очистка пробелов в `summary_osv_df`/`journal_df`
4. `_move_and_sort_level_columns(context)` (`base.py:501`) — `Level_*` в конец по возрастанию
5. `_validate_output(context)` (`base.py:293`) — запрет `object`-колонок (иначе `TypeError`). Приводите через `cast_columns_to_types()` (`utils/dataframe_utils.py:13`)
6. Контроль сходимости баланса: если есть `сальдо, тыс.ед.`, сумма проверяется на `0` с допуском `tolerance_balance` (дефолт `config/defaults.py:13`). Пропуск — через `self._skip_balance_validation = True` в `__init__` шага (`base.py:133`). Применяется в Step 2 и Step 2а, где данные неполные до добавления синтетических счетов, а также в шагах 20/21 (свёртка не меняет сходимость баланса). Для ОПУ-расходов — `_validate_against_osv()` в `base_expenses_step.py:471`.

Декоратор `handle_pipeline_errors` (`decorators.py:50`) пишет метрики в `context.step_metrics` и логирует сводку (`base.py:1058`, DEBUG).

### Единый стандарт для справочников, подтягиваемых по имени компании

Для справочников, данные которых выгружаются по имени компании (**ППА**, **СправочникУФР**, **ПланСчетовБУ**, **КредитОбслуж**), поведение при отсутствии данных приведено к единообразию:

* **Нет вообще записей по компании** — сразу выдаётся список недостающих для меппинга позиций (независимо от того, что записи по компании отсутствуют целиком). Для ППА (шаг 6) это перекрывает даже `STRICT_OS_GROUP_CHECK` — стоп со списком позиций; если меппинговых позиций в данных нет (нет аренды/лизинга) — WARNING и продолжение.
* **Записи есть, но список неполный** — прежняя логика: строгий режим -> стоп со списком недостающих позиций; мягкий -> WARNING + подстановка `не_указано` (для ППА — под управлением `STRICT_OS_GROUP_CHECK`).
* Во всех штатных остановках `problem_data` пишется в mismatches/ как список **недостающих позиций** (а не только список имеющихся компаний); подсказка «какие компании есть в справочнике» уходит в текст ошибки (лог).
* Единые хелперы в `pipeline/base.py`: `make_missing_values_problem_data(missing_by_type, company, source_by_type=None)` (формат отчёта: `отсутствующее_значение`/`тип`/`компания`; при `source_by_type={тип: (source_df, колонка_значения, [колонки_сумм])}` — добавляются `количество_строк` и суммы по позициям из ОСВ/журнала, чтобы пользователь оценил существенность перед мягким режимом) и `hint_companies_in_reference()` (подсказка со списком компаний).

## Классификация ошибок в логах ([STOP] vs CRITICAL)
Верхний обработчик `cli/main.py` разделяет штатные остановки и настоящие сбои:
* `except PipelineError` — предусмотренные ошибки пайплайна: `ProcessingStepError` с первопричиной-наследником `PipelineError` в `__cause__` (декоратор шагов сохраняет её; сама обёртка — тоже подкласс `PipelineError`, см. `pipeline/errors.py`) и «сырые» `PipelineError` вне шагов (например, `PeriodMismatchError` из Фазы 0). Лог — `ERROR [STOP] Обработка остановлена: <причина>` + подсказки про актуализацию справочников и mismatches/. CRITICAL не используется.
* `ProcessingStepError` с первопричиной НЕ из `PipelineError` и общий `except Exception` — непредвиденные сбои: `CRITICAL [!!] Неожиданная ошибка`.
* `FileNotFoundError` — `ERROR [STOP] Обработка остановлена: не найден файл...`.

Теги сообщений: `[STOP]` — штатная остановка конвейера (нужна актуализация справочников/входных данных), `[!!]` + CRITICAL — действительно непредвиденное падение. Сообщение о сохранении проблемных данных (`[FOLDER] Проблемные данные сохранены...`, `base.py:579`) — уровень INFO.

## Индивидуальный меппинг компаний (колонка «компания» в Меппинг_опу / Меппинг_бб)

Справочники меппинга универсальны для группы, но одна и та же статья/счёт может означать разное в разных компаниях. Реальный кейс: «Доходы (расходы), связанные со сдачей имущества в аренду (субаренду)» (счёт 91.02) у «ГиагКХП» — это проценты ППА, у остальных компаний — аренда. Тип «Аренда» входит в `ПрочиеДоходыНДС`, поэтому проценты уходили в обработку «продажи активов» и давали `mismatch_step_17_распределение_расходов_91_02_*` с контрагентом `не_указано`.

* **Правило.** В обоих листах есть колонка `компания` (`REFERENCE_SCOPE_COL` в `config/settings.py`, значение-«все» = `SCOPE_ALL_VALUE`): `все` (или пусто) — строка действует для всех компаний; имя компании из `КомпанииГруппы` — только для неё и **перекрывает** универсальную строку с тем же ключом листа (иначе в справочнике окажутся две строки с одним ключом и шаг 19 выберет произвольную). Строки других компаний отбрасываются.
* **Ключи перекрытия:** `Меппинг_опу` — `OpuReportConstants.REFERENCE_ROW_KEY` (`счет + доход_расход + сегмент + вид_связи`; это ключ **строки справочника**, не ключ поиска счёта ФО — он без `доход_расход`); `Меппинг_бб` — `BalanceReportConstants.MAPPING_KEYS` (9 колонок).
* **Где применяется:** `utils/reference_scope.py` → `resolve_company_view(df, company, key_cols, ...)` + `ScopeDiagnostics`. Вызывается **один раз на прогон** из `pipeline/executors.py` (`_apply_company_reference_scope()` в `initialize_context()`, сразу после `_validate_and_enrich_company_info`) для `меппинг_опу` и `меппинг_баланс` — поэтому шаги 4/5/7/8/9/13 (баланс) и 14/17/19 (ОПУ) читают уже готовый взгляд и править их не нужно. Порядок результата: универсальные (без перекрытых) → индивидуальные в конец (важно для `drop_duplicates(keep='first')` и `dict(zip(...))`).
* **Обратная совместимость:** кадр **не меняется вообще** только когда в справочнике нет строк, адресованных конкретным компаниям: нет колонки `компания`, нет ключевых колонок или все строки — `все` (тогда возвращается тот же объект). Так в `Меппинг_бб` можно оставлять колонку пустой для всех. **Строки других компаний отбрасываются всегда**, в том числе для компании, у которой нет ни одной своей строки — это отдельное правило, а не следствие наличия индивидуальных строк (см. баг ниже).
* **⚠️ Регресс 29.09.2026 — «ТимПФ»: строки чужих компаний протекали в прогон.** Ранний выход `if individual.empty: return df` возвращал **весь** справочник, включая строки других компаний: правило «отбросить чужие» работало только пока у компании есть свои строки (у «ГиагКХП» есть, поэтому её прогоны были зелёными). У «ТимПФ» (сегмент «Птицеводство», как и у «ГиагКХП») индивидуальных строк нет → статья «Доходы (расходы), связанные со сдачей имущества в аренду (субаренду)» давала **два** типа — «Аренда» (своя) и «Расходы по процентам аренда» («ГиагКХП»); ступени 2 (ППА) не подходила (корр.счета `19.09`/`23.01`/`68.02`), ступень 3 по сегменту тоже видела оба типа (сегменты совпадают) → `ReferenceMismatchError` и остановка шага 17. **Справочник был корректен, протекала фильтрация.** Не делайте так больше: отбрасывание чужих строк не должно зависеть от наличия своих. Счётчик — `ScopeDiagnostics.dropped_foreign_rows`.
* **Диагностика:** INFO «Индивидуальный меппинг …»; INFO «отброшены строки других компаний — N»; значения колонки, не совпадающие ни с `все`, ни с компаниями (опечатка в имени) — WARNING; Excel `mismatches/reference_scope_<компания>_<run_id>.xlsx` (листы «Применённые строки», «Перекрытые строки», «Индивидуальные без пары», «Неизвестные компании»); сводка `context.data['reference_scope_summary']` → строка «Индивидуальный меппинг компании» в разделе «СОСТОЯНИЕ ОТЧЁТА» титульного листа (`report_cover._reference_scope_text`). Запись в `entries` появляется и при одних отброшенных строках — иначе титульный лист врал бы «правок для компании нет» при фактической фильтрации.
* **Обе половины правки в отчёте.** Первые два листа — результат одной подмены: «Перекрытые строки» (что было) и «Применённые строки» (`ScopeDiagnostics.individual_frame` — что стало), поэтому подмену видно в самом файле, не открывая `Справочники.xlsx`. Имена листов/колонок объявлены константами `SCOPE_SHEET_COL`/`SCOPE_OVERRIDER_COL` и `SHEET_*` в `pipeline/executors.py` — не дублируйте строки в коде. Служебные колонки: `лист` (кадры `Меппинг_опу` и `Меппинг_бб` склеиваются через `pd.concat`, а колонки у них разные) и `перекрыто_компанией` (в перекрытых строках колонка `компания` всегда `все` и не отвечает, кто именно перекрыл статью). Файл создаётся только когда есть что показать; у компаний без индивидуальных строк его не бывает.
* **Загрузка справочников — по ИМЕНАМ колонок.** `REFERENCE_CONFIGS` (`config/settings.py`) задаёт `usecols` именами, а не индексами: позиционные индексы «съезжают» при вставке колонки в лист — после появления `компания` в кадр перестали попадать `счет_фо` (оба листа → шаг 19 и шаг 13) и `детализация_субконто` (`Меппинг_бб` → `KeyError` в шаге 4).
* **Тип ОПУ в шаге 17** выбирается тремя ступенями (`_step17_data._resolve_income_expense_mapping`, сегмент пробрасывается из `context.segment`): (1) единственный тип на ключ `счет[:5] + доход_расход`; (2) подтверждённый объект ППА (корр.счёт из `PPA_ACCOUNTS` + объект с префиксом `ППА`) → тип выбытия прав пользования; (3) тип из блока **сегмента компании**, если там ровно один; иначе прежний `ReferenceMismatchError` с `problem_data`. Ступень 3 — единственный способ, которым «ГиагКХП» получает «Расходы по процентам аренда», не смешиваясь с чужими сегментами общего блока.
* **Контрагенты процентов ППА:** шаг 17, `_step17_processing._pull_contractors_from_ppa_by_rbp()` — объект с признаком «ППА» (`Субконто Дт_1` для доходов, `Субконто Кт_1` для расходов) сопоставляется с колонкой `рбп` листа ППА по компании, контрагент подтягивается (в проводке на стороне Кт стоит 97.21, поэтому обычное извлечение контрагентов даёт `не_указано`). Уже проставленный контрагент не перезаписывается (вызов после `_process_ppa`). Объект с признаком «ППА», которого нет в `рбп`, — под `STRICT_PPA_MAPPING_CHECK`: `True` → `MissingMappingError` + Excel в mismatches/, `False` → отчёт + WARNING, шаг продолжается. **В диагностику идут только настоящие РБП-строки** (регресс 29.09.2026 «ТимПФ»): (1) `Корр.счет` противоположной стороны — 97.x; (2) объект не известен справочнику как ОС (`ос_ппа`/`ос_после_перехода_в_собственность`, хелпер `_collect_ppa_os_objects`). Иначе амортизация ОС (91.02 / Кт 02.03) и списания (Кт 01.09), где субконто называется «ППА ТЕК…», ловились маркером `PPA_OBJECT_MARKER` и давали ложный стоп. Проводки с исключёнными строками остаются с `не_указано` (по решению пользователя). Смоук — `_smoke_17_ppa_rbp_contractors.py` (6 сценарий: 2 на фильтры).
* **Смоуки:** `_smoke_reference_scope.py` (загрузка обоих листов новым конфигом + резолвер + реальные кейсы: «ГиагКХП» получает «Расходы по процентам аренда», компания **без** своих строк её не наследует — регрест кейса «ТимПФ»), `_smoke_17_segment_type.py` (три ступени выбора типа; реальный сценарий пропускается с помиской, если в `transaction_report` выгрузки не той компании — папка меняется от прогона к прогону), `_smoke_17_ppa_rbp_contractors.py` (заполнение контрагента, строгий/мягкий режим, амортизация 02.03 и объект из `ос_ппа` — не РБП).
