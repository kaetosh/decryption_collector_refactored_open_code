# Собиратель расшифровок (Decryption Collector)

Приложение собирает **расшифровку баланса** и **расшифровку ОПУ** из выгрузок 1С
(оборотно-сальдовые ведомости, карточки счетов, отчёты по проводкам), обогащает
их классификационными признаками из справочников и формирует итоговый Excel-отчёт.

Проект функционально завершён: новые отчёты не планируются, развивается только
исправление ошибок и поддержка. Архитектура рассчитана на быструю локализацию
сбоев по результатам тестирования.

## Как работает приложение

Выполнение состоит из трёх фаз с двумя паузами (`cli/main.py`):

1. **ФАЗА 0** — ожидание выгрузок из 1С в папке `_INPUT_DATA/00_inbox`;
   после нажатия Enter автосортировка переносит Общую ОСВ в `general_osv`
   (см. «Автосортировка выгрузок»), затем — инициализация контекста,
   загрузка допусков сходимости (лист «Параметры» в `Справочники.xlsx`,
   при отсутствии — значения из `config/defaults.py`).
2. **ФАЗА 1** — конвейер подготовки (шаг 1a): формирование списка выгрузок из 1С
   и сохранение его в Excel.
   **Пауза** — бухгалтер выгружает перечисленные файлы из 1С в `00_inbox`;
   после нажатия Enter автосортировка раскладывает их по целевым папкам.
3. **ФАЗА 2** — основной конвейер (шаги 1b–19): проверка файлов, загрузка,
   классификация, сборка расшифровок баланса и ОПУ. Все результаты запуска
   сохраняются в отдельную папку `_OUTPUT_DATA/run_ГГГГММДД_ЧЧММСС`
   (см. «Выводные данные»).

## Автосортировка выгрузок (`00_inbox`)

Пользователь выгружает файлы из 1С **одним движением** в папку
`_INPUT_DATA/00_inbox` — без разбора, что куда. Скрипт сам раскладывает
файлы по целевым подпапкам (`io_module/auto_sort.py`):

- **Волна 1** (в `pause_for_osv_general_export`, до Фазы 0): файлы
  с `_общаяосв_` в имени переносятся из inbox в `general_osv`; из
  `general_osv` в архив убирается всё, что не похоже на Общую ОСВ.
- **Волна 2** (в `pause_for_1c_export`, после шага 1a): источник истины —
  список выгрузок `Выгрузить_<компания>_<период>.xlsx` (оба листа:
  «Обязательные выгрузки» и «Спецотчеты», колонки «Имя файла для
  сохранения» → «Куда класть»; колонки ищутся без учёта регистра
  — в реале на листе 1 это `куда класть`, а на листе 2 заголовок
  в третьей строке из-за двух служебных строк сверху). Файлы inbox
  переносятся по назначению; файлы, уже лежащие в правильной папке,
  не трогаются; «кривые» имена (пробелы, регистр, без хвостового `_`)
  при совпадении со списком приводятся к эталонному имени; копия общей
  ОСВ из inbox (её нет в списке) — в `general_osv`; хвосты прошлых сессий
  в целевых папках и нераспознанные файлы inbox переносятся в архив.

Правила:

- Классификация детерминированная — по имени файла, содержимое не читается.
- Ничего не удаляется безвозвратно: левое/старое/перезаписанные версии —
  в `_INPUT_DATA/_archive/<run_id>/<имя_папки>/`, нераспознанное — в
  `.../unsorted/` с WARNING в логе. Конвейер не останавливается — нехватку
  обязательных файлов штатно сообщит шаг 1b.
- Конфликт имён: идентичное содержимое — дубликат удаляется; отличающееся —
  старая версия в архив, новая занимает место (WARNING). Файл списка
  `Выгрузить_*.xlsx` и `~$`-файлы Excel из inbox не трогаются.
- Каждая волна пишет `sort_report.xlsx` (файл/действие/откуда/куда) в папку
  запуска и INFO-сводку в лог.
- Отключение: `AUTO_SORT_ENABLED = False` (`config/settings.py`) — прежнее
  поведение (пользователь раскладывает файлы вручную).

## Конвейер обработки (Фаза 2)

Состав конвейера задаётся в `pipeline/factories.py`. Шаги сгруппированы по этапам:

| Этап | Шаги | Назначение |
|---|---|---|
| Загрузка и подготовка | 1b, 1c, 2 | проверка выгрузок, сверка итогов, плоская сводная ОСВ |
| Классификация баланса | 3–9 | счёт, тип/подвид задолженности, группа ОС, долг/короткая часть, биоактивы, связанные стороны |
| Спецрасчёты баланса | 10, 11, 11a, 12 | источник аренды/лизинга, разделение счёта 60, проверка похожих контрагентов, разделение счёта 84 |
| Сборка баланса | 13 | расшифровка баланса («Баланс») |
| Классификация ОПУ | 14–18 | основа ОПУ (90.01/90.02), управленческие, коммерческие, прочие (91), налог и движения (99) |
| Сборка ОПУ | 19 | итоговая расшифровка ОПУ |

### Жизненный цикл шага

`Step.execute()` (`pipeline/base.py` + декоратор в `pipeline/decorators.py`):

```
валидация входа → _process() (бизнес-логика шага) → очистка пробелов
→ move_and_sort_level_columns → валидация выхода
```

Доступ к таблицам предыдущих шагов — через
`self.get_df_from_context(context, key, hint)`: при отсутствии или пустоте
таблицы возникает понятная ошибка с именем ключа и подсказкой.

### Обработка ошибок (handle_pipeline_errors)

| Исключение | Поведение |
|---|---|
| `MissingContractorError` | строгий режим (`STRICT_CONTRACTOR_CHECK=True`) — сбой; мягкий — отчёт в Excel + замена на «3 лица», шаг продолжается (статус `soft`) |
| `MissingCreditContractorError` (КредитОбслуж, шаг 17) | строгий режим (`STRICT_CREDIT_CONTRACTOR_CHECK=True`, по умолчанию) — отчёт в Excel + сбой; мягкий — отчёт в Excel + замена контрагента на «3 лица», шаг продолжается |
| `MissingOSGroupError` (ППА, шаг 6) | если по компании в справочнике вообще нет записей — **всегда сбой** со списком недостающих позиций (договоры аренды 76.07/76.05.3, РБП 97.21), независимо от `STRICT_OS_GROUP_CHECK`; если меппинговых позиций в данных нет — предупреждение, шаг продолжается. Если записи есть, но список неполный: строгий режим (`STRICT_OS_GROUP_CHECK=True`) — сбой; мягкий — предупреждение в лог, замена на «не_указано» внутри шага |
| `ConvergenceError` (увязка ЧП=НРП, шаг 19) | мягкий режим (`EXPORT_REPORT_ON_MISMATCH=True`, по умолчанию) — ошибка в лог, отчёт выгружается «как есть» для анализа расхождения; строгий (`False`) — отчёт в Excel (mismatches/) + сбой |
| `ReferenceMismatchError` и подвиды (`MissingMappingError`, `ConvergenceError`, `MissingSubtypeError`) | проблемные строки сохраняются в Excel, шаг падает с `ProcessingStepError` |
| `ReferenceMismatchError` (необязательные спецотчёты, шаги 7/11) | мягкий режим (`SKIP_OPTIONAL_SPECIAL_REPORTS_ON_ERROR=True`, по умолчанию) — отчёт в Excel (mismatches/) + предупреждение «проверьте файл на полноту и формат», шаг продолжается без этой детализации; строгий (`False`) — сбой |
| `ReferenceMismatchError` (ПланСчетовБУ, шаги 1c/17) | вместо сырого `ValueError` — штатный `[STOP]`: нет записей по компании → список компаний в справочнике; нет субконто «Контрагенты» → строки плана по компании; нет синтетических счетов из общей ОСВ → `MissingMappingError` со списком счетов |
| `MissingMappingError` (шаг 17, ППА) | при отсутствии записей по компании (в т.ч. пустом справочнике) и при неполном списке — недостающие объекты ОС по `ос_ппа`/`ос_после_перехода_в_собственность` + подсказка со списком компаний |
| `MissingFilesError` / `MissingCardError` | отчёт об отсутствующих файлах в Excel, сбой |
| `TooManyFilesError` | отчёт об избыточных файлах в Excel (mismatches/), сбой. Возникает, когда в папке найдено более одного файла по паттерну (например, два файла общей ОСВ) |
| `Exception` | заворачивается в `ProcessingStepError`, оригинал — в `__cause__` |

Иерархия и атрибуты исключений — в `pipeline/errors.py`. Появление нового типа
ошибки: добавить класс в `errors.py` и ветку в `decorators.py`.

### Классификация ошибок в логах ([STOP] vs CRITICAL)

Верхний обработчик `cli/main.py` различает штатные остановки и настоящие сбои:

- Предусмотренные ошибки пайплайна (наследники `PipelineError`: несоответствие
  справочникам, отсутствующие/избыточные файлы и т.д.) — в лог пишется
  `ERROR [STOP] Обработка остановлена: <причина>` и подсказки: дальнейшая обработка
  невозможна, пока не актуализированы справочники/входные данные; список проблемных
  значений — в `mismatches/` папки запуска. Статус CRITICAL не используется.
- Ошибки обработки необязательных спецотчётов (`арендареклассдолгкорт_7697`,
  `лизингреклассдолгкорт_7697`, `осв_60инвест`, `реклассдолгкорт_97`; шаги 7 и 11)
  при `SKIP_OPTIONAL_SPECIAL_REPORTS_ON_ERROR=True` (по умолчанию) конвейер
  не останавливают: WARNING «проверьте файл на полноту и формат», шаг продолжается
  без этой детализации (`Step._run_optional_special_report`, `pipeline/base.py`).
- Непредвиденные исключения (первопричина шага — не `PipelineError`, либо ошибка
  вне шагов, не относящаяся к пайплайну) — `CRITICAL [!!] Неожиданная ошибка: ...`.
- Сообщение о сохранении проблемных данных (`[FOLDER] Проблемные данные сохранены
  в: mismatches/...`) — уровень INFO: это не ошибка, а указатель на отчёт.

### Проверка периода отчётности на этапе инициализации

При инициализации контекста (`pipeline/executors.py`, `_validate_and_enrich_company_info`)
значение `context.period` (извлечённое из имени файла общей ОСВ) сверяется с полем
`период_отчетности` листа «КомпанииГруппы» справочника по строке соответствующей
компании. Сравнение — посимвольное после очистки пробелов.

При несовпадении выбрасывается `PeriodMismatchError` (подвид `ReferenceMismatchError`).
Эта проверка находится вне этапов пайплайна (не проходит через `handle_pipeline_errors`),
поэтому её перехватывает верхний обработчик `cli/main.py`: как предусмотренная ошибка
пайплайна (`PipelineError`) она логируется как `ERROR [STOP] Обработка остановлена: ...`
(код выхода 1) — без статуса CRITICAL. CRITICAL `[!!] Неожиданная ошибка` остаётся только
для непредвиденных сбоев (первопричина — не наследник `PipelineError`).

## Отладка

- **Консоль** — уровень INFO (сообщения для пользователя).
- **`app.log`** — уровень DEBUG, перезаписывается при каждом запуске
  (`logging_handling/logger_config.py`). Здесь же — техническая сводка шагов.
- **Сводка шагов** (DEBUG, в конце работы): имя шага, статус (`ok` / `soft` /
  `error`), время выполнения, число строк таблиц после шага:

  ```
  === Сводка шагов конвейера 'Основной конвейер...' (итого: 84.5 сек) ===
    Шаг 11: Разделение счёта 60…     ok     9.26 сек | строк: journal_df=12500, data.mapping=412
  ```

  Метрики пишутся в `context.step_metrics` (метод `record_step`).
- **Проблемные данные** — при ошибках справочников автоматически сохраняются
  в Excel (внутри папки запуска, подпапка `mismatches/`): можно сразу править
  `Справочники.xlsx` и перезапускать.
- **Traceback** — флаг `-t` (или интерактивный ответ «y») включает полный стектрейс.
- Ошибки шага доступны по цепочке: `ProcessingStepError.__cause__` — исходное исключение.

## Выводные данные

Каждый запуск приложения пишет все свои результаты в отдельную папку
`_OUTPUT_DATA/run_ГГГГММДД_ЧЧММСС` (логика — в `io_module/output_manager.py`):

```
_OUTPUT_DATA/
└── run_20260828_142840/
    ├── 0096_Расшифровка_баланса_..._2025.xlsx      # итоговый отчёт: баланс + ОПУ
    ├── Выгрузить_<компания>_<период>.xlsx          # список выгрузок из 1С (шаг 1a)
    ├── ведомостьОС_обработка_..._.xlsx             # обработанная ведомость ОС (шаг 10)
    ├── validation_mismatches_..._<run_id>.xlsx     # расхождения валидации (шаг 7)
    ├── unknown_contractors_60_invest_<run_id>.xlsx # неизвестные контрагенты (шаг 11)
    ├── warnings/
    │   └── WARNING_similar_contractors_..._.xlsx   # похожие контрагенты (шаг 11a)
    └── mismatches/                                 # ошибки справочников и файлов
        ├── mismatch_<шаг>_<справочник>_<run_id>.xlsx
        └── missing_files_<шаг>_<run_id>.xlsx
```

Хвост `<run_id>` (`_20260828_142840`) в именах проблемных файлов — идентификатор
запуска, он совпадает с именем папки запуска: файлы легко сопоставить с прогоном.

**Хранение:** константа `KEEP_LAST_RUNS` в `config/settings.py` (диапазон 1–5,
по умолчанию 5). При старте нового запуска папки прошлых запусков сверх лимита
удаляются. Безопасность:

- удаляются **только** папки с именами `run_*`; любые другие файлы и подпапки
  `_OUTPUT_DATA` (в том числе оставшиеся от прежних версий программы) не
  затрагиваются;
- папка, занятая другой программой (файл открыт в Excel), пропускается
  с предупреждением и будет удалена при одном из следующих запусков.
